## 1. 背景与问题

### 1.1 用户反馈

> 「在角色卡中的调整等级我认为仅仅有滑动框不够，因为实际的需求可能是用户的等级调整都是 +1 −1 这么调整，所以这个滑动根本不适合这种操作，而这种操作又在纯职业中特别明显。」

### 1.2 现状取证

| 事实 | 依据 |
| --- | --- |
| 等级操作区只有一条滑杆（松手提交），没有 ±1 入口 | `ClassAllocationControl.vue:328-344`（`input[type="range"]`） |
| 逐职业 `− N ＋` 步进**只在兼职生效且 ≥2 职业时**渲染 | `ClassAllocationControl.vue:357` 的 `v-if="multiclassActive"`；`isMulticlassActive()` = `enabled && classes.length > 1`（`rules/multiclass.ts:109-113`） |
| 因此**纯职业**（未启用兼职，或启用了但只有 1 个职业）整块职业行不渲染 → 只剩滑杆 | 同上；既有测试「单职业模式不显示职业步进列表」（`test/components/ClassAllocationControl.test.ts:90`）固化了这一点 |
| 滑杆在触屏／移动端是「拖动—对准—松手」三步，且容易滑过目标档位 | 交互形态本身；±1 是升级/降级的高频动作 |

补充：角色卡的「调整等级」弹窗（`LevelAdjustModal.vue`）内嵌的正是同一个控件，所以纯职业玩家在角色卡上确实没有任何 ±1 入口。

### 1.3 影响

- 纯职业（最常见）升级/降级只能靠滑杆微调，操作成本与误操作概率都高于应有的水平。
- 兼职玩家在职业行里有 ±1，但**总等级**没有 ±1；跨职业分配时仍需滑杆。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 等级卡 | 控件内承载等级滑杆与等级读数的卡片（本次在其头部加入步进） |
| 步进 | 新加的 `−`／`＋` 按钮，每次改变 1 级 |
| 总等级 | 各职业等级之和（`getTotalLevel`）；无职业时为 `targetLevel` |
| 轻量确认策略 | 滑杆既有策略（需求 §3.4）：仅当有选择将失效时才弹确认 |

## 3. 需求一：等级卡内增加 ±1 步进（决策 D34）

### 3.1 R1 位置与形态

- 在等级卡**头部**增加一行：左侧为等级标签（兼职时「总等级」，否则「目标等级」），右侧为步进控件 `−  N级  ＋`。
- **单职业、无职业、兼职三种状态都显示**；不再依赖 `multiclassActive`。
- 步进按钮复用 `BaseButton variant="secondary"`（既有最小高度 3rem，满足触屏点击目标），与职业行步进保持同一视觉语言。

### 3.2 R2 值口径与边界

- 显示值与滑杆**同一个**：无职业时取 `targetLevel`，有职业时取各职业等级之和。
- 边界复用 `getTotalLevelBounds()`：无职业 1—20；有职业时下限 = 职业数量、上限 = 20（角色总等级上限）。
- 到达边界时对应按钮**禁用**（1 级不能再降、20 级不能再升、兼职达下限不能再降）；禁用时不产生任何事件。
- 继承既有约束：调整**不会移除职业**（下限即职业数量；起始职业 1 级时不可再降）。

### 3.3 R3 兼职时沿用滑杆的加级规则

- 兼职状态下 `＋` 与滑杆同口径：**加级给列表最后一个职业，减级从末尾往前扣**（`rules/multiclass.ts` 的 `setTotalLevel` 语义），不引入第二套分配规则。
- 因此兼职时「总等级 ±1」与「某个职业 ±1」是两种入口，互不冲突：前者用于快速升降总量，后者用于精确分配到某一职业。

### 3.4 R4 不替代滑杆

- 滑杆保留（大跨度跳级仍靠它），本次只**增加**入口，不改变它的形态与提交时机（仍是松手提交）。

## 4. 需求二：提交策略与引导沿用（决策 D35）

### 4.1 R5 与滑杆同一条提交通道

- 步进提交 `applyTotalLevel` 事件（**不走** `apply`），因此页面沿用既有的轻量确认策略：
  - 单纯 ±1（无选择失效）→ 立即生效，不弹确认；
  - 有选择将失效（例如降级会作废超限属性提升）→ 仍弹依赖影响确认弹窗。
- 理由：±1 是高频连续操作；若每次都走 `apply`（`alwaysConfirm: true`，D7 防误触策略）会每次弹确认，与「快速微调」的目标相反。`apply` 的防误触语义仍由「添加/移除职业、切换起始职业、关闭兼职」承担，不变。

### 4.2 R6 引导沿用上一批决策

- ±1 升级产生新增检查点时，按[角色卡等级调整后的检查点引导需求](角色卡等级调整后的检查点引导需求.md) D29 处理：**只出引导条、不自动跳转**（滑杆路径同款），因为连续微调不应该把用户带离角色卡。
- 降级产生的复查引导条同样沿用该批规则。

### 4.3 R7 两种模式一致

- 弹窗模式（角色卡「调整等级」）与内联模式（第 1 步／第 3 步）行为一致。
- 内联模式下若页面未采纳本次提交（依赖确认被取消），显示与滑杆一样**回到已提交值**（`PC-B` R3／D21 的既有不变式），不残留未生效的显示。

- 不改滑杆形态、提交时机与既有 `sliderLevel` 本地预览语义。

## 6. 验收标准

1. 纯职业（未启用兼职，或兼职启用但只有 1 个职业）时等级卡出现 `− / ＋` 步进：点 ＋ 一次总等级 +1，点 − 一次 −1。
2. 兼职（≥2 职业）时同样出现步进，且 ＋ 加给列表最后一个职业、− 从末尾往前扣，**不会移除职业**（与滑杆一致）。
3. 无职业（第 1 步）时步进改的是目标等级（`targetLevel`），范围 1—20。
4. 到边界时对应按钮禁用且不产生事件：1 级时 − 禁用；20 级时 ＋ 禁用；兼职达下限（= 职业数量）时 − 禁用。
5. 单纯 ±1 不弹确认弹窗；步进只发 `applyTotalLevel`，不发 `apply`（确认策略区分保持不变）。
6. ±1 升级有新增检查点时按 D29 出引导条但不跳转；降级有失效项时仍弹确认。
7. 内联模式下页面未采纳时，显示回到已提交值（与滑杆同一不变式）；弹窗模式下本地待定摘要（「本次变更」）随之更新。
8. 步进按钮有中文 `aria-label`（如「目标等级升一级／降一级」「总等级升一级／降一级」），可键盘聚焦触发；点击目标 ≥ 3rem。
9. `npx vue-tsc -b`、`npx vitest run`、`npm run build` 全部通过；既有测试无回归（改写的断言需说明理由）。
10. 版本号保持 1.13.0；未新增模块（拓扑复核结论写明「已复核／无需更新」）。
