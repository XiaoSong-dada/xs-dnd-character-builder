## 0. 结论摘要

1. **三条需求都定位到明确根因**：R1 是「完整目录」复用了规则库登记顺序（推荐项被打散）；R2 是 v1.9.0 新写的筛选行固定最小列宽（12rem + 4×7rem ≈ 42rem）超过 32rem 车卡容器，且列数只按**视口宽度**切换，所以 iPad 与 Windows 上必然溢出；R3 是吸底栏给「当前角色」框写死 4.75rem 让位高度，提示行一出现就把栏顶高约 1.47rem（≈23.5px），盖住当前角色框底部。
2. **三条需求都不改规则、不改草稿结构、不改校验口径**：只涉及展示顺序、CSS 布局与外壳结构。
3. **决策已确认（2026-09-21，见 §5）**：D1 完整目录与搜索结果统一「推荐在前」；D2 法术步骤内容收进 32rem 容器而不放宽版心；D3 未完成提示保留在吸底栏，改为抽屉与操作栏同块吸底；D4「去完成」在起源与法术两步统一为「切换到首个未完成任务 + 聚焦任务标题」；D5 本期不截断偏长的 blocker 提示；D6 随 R2 在 `docs/rules.md` 补一条排版口径。
4. R2 是 v1.9.0 引入的回归（`git show HEAD` 显示筛选行由 `minmax(0, 1fr) minmax(8rem, auto)` 改为 5 列固定最小宽），R1、R3 属于 v1.9.0 新交互带来的既有缺口；R3 还含一处交互不一致——法术步骤的「去完成」只是锚点跳转（`#builder-step-tasks`），起源步骤则会切换任务并聚焦标题。

## 2. R1：种族／背景「查看全部」后的推荐置顶排序

### 2.1 现象

点「查看全部 N 项」后，候选项按规则库登记顺序平铺，带「推荐」徽标的条目与其它条目交错出现（例如 2014 战士视角下，矮人→精灵→半身人→人类→龙裔……），玩家看不出哪些是推荐项。

### 2.2 根因

`OriginStep.vue` 的 `visibleRaces` / `visibleBackgrounds` 用同一个 `full` 开关切换候选池：

- 非完整模式：`pool = recommendedRaces`（推荐项前 6 条，或没有推荐时的前 6 条）——顺序已经是推荐在前；
- 完整模式（`showAllRaces`／有搜索词／来源筛选非「全部」）：`pool = filteredRaces`，直接沿用 `repository.races` 的登记顺序，**没有再做推荐分区**。

即：推荐排序只存在于「默认视图」，完整目录视图丢掉了它；搜索与来源筛选与「查看全部」共用同一条分支，所以问题同样存在。

### 2.3 需求条目

- **R1-1 排序规则**：完整目录视图（点「查看全部」）与搜索／来源筛选结果统一采用**稳定分区排序**：`推荐分组在前，其余沿用规则库登记顺序`。同一分组内保持原有相对顺序（不按名称、不按 `localeCompare` 重排），保证不同环境下顺序一致。
- **R1-2 推荐判定**：沿用现有规则数据判定 `recommendedClassIds.includes(当前职业 ID)`；未选择职业时不产生推荐分组，整体保持规则库登记顺序（不得把未选职业误判为推荐或全部推荐）。
- **R1-3 默认视图不变**：未展开时的行为保持不变——保留已选摘要卡、最多展示 6 个推荐项（无推荐时取前 6 项）、按钮文案与计数 `查看全部 {{ filteredRaces.length }} 项` 均不变。
- **R1-4 已选与隐藏规则不变**：候选中仍隐藏当前已选项（`item.id !== raceId` / `backgroundId`），已选摘要卡仍固定在最上方；本次只改顺序，不改过滤条件。
- **R1-5 实现位置**：排序必须是框架无关的纯函数，放在规则层 `app/src/rules/recommend.ts`（推荐理由函数已在该文件），并提供单元测试；组件只消费结果，不在模板或 `v-for` 中做排序。该口径沿用既有基线「推荐只用于排序、不限制选择；排序计算放规则层，组件经 `computed` 消费」（[玩法偏好与职业推荐完善需求](归档需求/玩法偏好与职业推荐完善需求.md) §R2 第 5 条／§R5 第 2 条）。
- **R1-6 规则集一致**：`5e-2014` 种族与 `5e-2024` 物种、两个规则集的背景行为一致；调用方不得出现两套排序实现。
- **R1-7 文档同步**：更新 `docs/dnd-species.md`（第 20 行）、`docs/dnd-backgrounds.md`（第 25 行）与 `docs/rules.md`（第 192 行）的口径，明确「完整目录与搜索结果同样推荐优先，其余保持登记顺序」。

### 2.4 非目标

- 不引入评分、算法排序或新的推荐数据；不改 `recommendedClassIds` 内容与 6 项上限。
- 不改搜索匹配规则（中英文名、来源筛选语义）与空状态文案。
- 不把该排序推广到职业列表（职业页按稳定配置顺序展示，见 `docs/rules.md` 第 189 行）或法术候选列表。

### 2.5 验收

| 编号 | 验收项 | 检查方式 |
| --- | --- | --- |
| R1-A1 | 完整目录中推荐项全部位于非推荐项之前 | 规则层单测（2014 种族、2024 物种、2014／2024 背景各一组） |
| R1-A2 | 同一分组内相对顺序与输入（规则库登记顺序）一致，函数不修改入参 | 单测（含乱序输入、空输入、无职业 ID） |
| R1-A3 | 组件层：点「查看全部」后列表头部为推荐项且带「推荐」徽标；默认 6 项视图与已选摘要不变 | `app/test/components/OriginStep.test.ts` 扩展断言 |
| R1-A4 | 搜索／来源筛选结果同样推荐在前 | 规则层单测 + 组件测试抽查 |

## 3. R2：法术步骤页面宽度超出上下栏（Windows／iPad）

### 3.1 现象

在 Windows 桌面浏览器与 iPad 上，第 8 步「配置职业法术」页面的内容明显比顶部步骤头（「第8步 配置职业法术」）和底部吸底栏（「上一步 / 继续」）更宽：筛选行向右伸出车卡容器，iPad 竖屏（768px）下最右侧的下拉控件还被视口边缘裁掉。

### 3.2 根因（可复算）

1. **车卡容器是固定宽度单列**：`QuickBuildShell` 为 `width: min(100%, 32rem)` = 512px，内容区左右各 1rem 内边距 → 内容盒 **30rem = 480px**。步骤头与吸底栏都在同一容器内，宽度同为 512px。
2. **筛选行要求 42rem**：`SpellcastingStep.vue` L230 为
   `grid-template-columns: minmax(12rem, 2fr) repeat(4, minmax(7rem, 1fr)); gap: 0.5rem;`
   最小需求宽度 = 12rem + 4×7rem + 4×0.5rem = **42rem = 672px**，超出内容盒 12rem（192px）。
3. **列数只看视口，不看容器**：L233—234 的两个断点是 `@media (max-width: 760px)` 与 `@media (max-width: 430px)`。容器恒为 512px，但 iPad 竖屏 768px、iPad 横屏 1024px、Windows 桌面都 > 760px，于是**永远走 5 列**分支。
4. **溢出表现**：容器只有 `overflow-x: hidden`（`MainLayout.vue` L42），所以不会出现横向滚动条，而是筛选行直接越过上下栏右边界；iPad 竖屏（768px）时右边缘 816px > 768px，最右侧控件被视口裁切。
5. **属于 v1.9.0 回归**：`git show HEAD -- .../SpellcastingStep.vue` 显示该规则由 `minmax(0, 1fr) minmax(8rem, auto)`（两列，可收缩，不溢出）改为当前的 5 列固定最小宽。

### 3.3 需求条目

- **R2-1 不溢出容器**：法术步骤的所有内容（含筛选行、摘要头、已选区、候选卡）必须在 32rem 车卡容器内自适应；在 375／430／768／1024／1440px 等宽度下都不得超过容器右边界，也不得被视口裁切。
- **R2-2 容器内自适应列数**：筛选控件改为按**容器宽度**排布——搜索框独占整行，其余下拉（来源／学派／仪式／专注，按元数据条件出现）自动换列；实现建议使用 `repeat(auto-fit, minmax(min(100%, 9rem), 1fr))` 一类可收缩列定义或容器查询，**不得**再用 `max-width` 视口断点决定列数。
- **R2-3 触控与收缩约定保留**：控件 `min-height: 2.75rem` 与 `min-width: 0`（防止长来源名／长学派名撑宽列）保持不变；控件数量仍随元数据条件增减，不影响布局稳定性。
- **R2-4 容器宽度口径不变**：不放宽车卡容器（32rem）、不改动其它 10 个步骤的版心；本需求只修法术步骤自身的列定义。
- **R2-5 同类风险自查**：一并确认第 4／8 步其余控件无同类固定最小列宽（已核对：`OriginStep.__filters` 为 `minmax(0, 1fr) minmax(8rem, auto)`、`SelectionTaskNavigator` 为 `repeat(2|3, minmax(0, 1fr))`、法术摘要头为 flex，均无同类问题）；若实施中发现新的溢出源，同样纳入本次修复。
- **R2-6 防回归（自动化）**：按项目既有「源码契约断言」方式（参见 `app/test/components/ui/ExpandableOptionCard.test.ts` 第 101—113 行）增加测试：断言筛选行不出现「固定 rem 最小列宽 ≥ 8rem」，且不再以视口 `max-width` 断点切换列数；同时断言 `QuickBuildShell` 的 32rem 容器宽度契约。
- **R2-7 样式组织**：保持 SCSS 嵌套写法（媒体／容器查询写在 `&__filters` 内），不新增顶层平铺选择器（`docs/rules.md`／AGENTS「UI 与移动端约定」）。
- **R2-8 文档同步（D6 已确认）**：在 `docs/rules.md` 的 UI／界面约定处补一条排版口径——车卡等固定宽度单列容器内的多控件筛选行必须按**容器宽度**自适应，禁止以视口 `max-width` 断点切换列数或使用固定 rem 最小列宽；供后续新增筛选行直接引用。

### 3.4 非目标

- 不重排法术步骤的信息层级、不改筛选维度与筛选语义、不改 `UiTabs` 环级页签行为。
- 不为桌面端单独设计多栏页面（车卡全流程保持单列手机优先版心）。

### 3.5 验收

| 编号 | 验收项 | 检查方式 |

| R2-A1 | 筛选行最小需求宽度 ≤ 容器内容宽度（30rem），即列表可收缩 | 源码契约测试（解析列定义并计算最小宽度上限） |
| R2-A2 | 筛选行不再含 `@media (max-width: …)` 视口断点，改用容器自适应 | 源码契约测试 |

## 4. R3：「法术选择尚未完成…去完成」遮挡当前角色框

### 4.1 现象

第 8 步法术未选齐时，吸底栏出现提示行「法术选择尚未完成，请按任务清单补齐。去完成」；该提示行会**压到「当前角色」可展开框上**，把当前角色框底部（含右侧「完成度」文字区）盖住。第 4 步出现 blocker 提示时同样成立，提示为两行时遮挡更多。

### 4.2 根因（可复算）

1. **抽屉让位高度是写死的常量**：`QuickBuildShell` 在「抽屉 + 操作栏」同时存在时给抽屉设 `bottom: 4.75rem`（L32），即假定操作栏恒定高 4.75rem。
2. **操作栏高度随提示行变化**：`StickyActionBar` = 1px 上边框 + `padding 0.75rem` + 内容 + `padding 0.75rem`，按钮 `BaseButton` 最小高 3rem（`BaseButton.vue` L30）。
   - 无提示行：1px + 0.75 + 3 + 0.75 ≈ **4.56rem**，低于 4.75rem 让位值，余量约 3px —— 正常。
   - 一行提示：再加 0.72rem×1.4 行高（1.008rem）+ 0.65rem 行距 ≈ **6.22rem（≈99.5px）**，比让位值高 1.47rem ≈ **23.5px**。
   - 两行提示（起源步骤 blocker 文案较长时）：约 **7.23rem**，侵入约 39.7px。
3. **谁盖住谁**：抽屉与操作栏都是 `position: sticky; z-index: 5`，操作栏在 DOM 中靠后 → 绘制在上层（L34—39）。因此超出的部分直接盖在抽屉底部；`CharacterDrawer` 摘要行最小高 4.5rem（72px），被盖住的正是摘要行下沿与「完成度」标签区，展开时还会盖住数值瓦片行底部。
4. **触发条件**：法术列表很长、页面必然可滚动 → 吸底栏被钉在视口底部 → 遮挡稳定复现；`index.vue` L250—251 的提示只在**该步未完成**时出现（无施法能力／未到施法等级时 `validateSpellSelections` 直接返回 `true`，不会出现提示行）。

### 4.3 需求条目

- **R3-1 不被遮挡**：无论提示行有 0 行／1 行／多行，也无论是否存在底部安全区（`env(safe-area-inset-bottom)`），「当前角色」框都必须完整可见且位于吸底操作栏正上方，不得被覆盖。
- **R3-2 结构口径（D3 已确认）**：抽屉与操作栏改为**同一块吸底区域**（同一 sticky 容器内上下排列），移除「抽屉写死 `bottom: 4.75rem`」的让位方式；操作栏高度变化时抽屉自动上移，不再依赖常量对齐。
- **R3-3 内容留白校准**：内容区底部留白改为与吸底区域的实际高度一致（或由流程内占位承担），保证页面最后一条内容不被吸底区域永久遮住；`QuickBuildShell` 现有的 `--drawer`／`--actions`／组合态三档 `padding-bottom`（6.5rem／6rem／10.5rem）需重新校准或改为按实际高度计算，避免同一处再出现「常量与实际高度不一致」。
- **R3-4 层级与展开态**：吸底区域整体仍在内容之上（保持现有 z-index 语义）；抽屉展开态（`max-height: 70dvh`）内容可滚动，`×` 关闭按钮保持可点。
- **R3-5 提示文案不变**：提示文案仍由页面传入（起源步骤用 blocker 文案、法术步骤用「法术选择尚未完成，请按任务清单补齐。」）；本期**不截断**偏长文案（D5），多行场景由 R3-2 的结构修复覆盖。
- **R3-6 「去完成」统一为「切换 + 聚焦」（D4 已确认）**：起源与法术两步的「去完成」行为一致——先切换到本步首个未完成任务（全部必选已完成时回落到第一个任务，沿用 `useSelectionTaskFlow.focusFirstIncomplete` 的既有语义），随后聚焦该任务面板标题（`<h2 tabindex="-1">`）使面板进入视野；**不再**使用 `<a href="#builder-step-tasks">` 的纯锚点跳转。
- **R3-7 重复点击仍生效**：当首个未完成任务已是活动任务、任务 ID 不变时，点击「去完成」也要把焦点／视图带回到该任务，不得因为 `activeTaskId` 未变化而完全无反应。
- **R3-8 分层与复用约束**：任务切换与聚焦仍由页面私有 hook `useSelectionTaskFlow` 提供，吸底栏只负责渲染并向上发出动作事件；`features/quick-build/**` 不得导入 `views/**`（依赖方向）。实现可在两种等价方案中择一（由实施计划决定，不得两者并存）：① 吸底栏 `emit` 动作事件 → `index.vue` 经步骤组件暴露的方法（`defineExpose`）调用 `focusFirstIncomplete`；② 页面 hook 维护一个「聚焦信号」经 prop 传入步骤组件，组件 `watch` 后调用同一方法。**不得**在吸底栏内复制一份任务选择逻辑。
- **R3-9 无任务时不出现动作**：步骤没有可切换任务时（`tasks` 为空）不渲染「去完成」动作，避免出现无效按钮。
- **R3-10 无障碍与触控不变**：抽屉摘要按钮保留 `aria-expanded`，关闭按钮保留 `aria-label="关闭抽屉"`，主要点击目标仍 ≥ 2.75rem；「去完成」由 `<a>` 改为 `<button type="button">` 后仍需键盘可达并有可见焦点态。
- **R3-11 防回归（自动化）**：新增契约断言——① `QuickBuildShell` 中抽屉与操作栏处于同一个 sticky 容器内；② 抽屉不再声明固定 `bottom` 让位值；③ 组件测试断言提示行存在时抽屉与操作栏为相邻兄弟节点（DOM 结构可直接断言，无需布局计算）；④ 吸底栏「去完成」为按钮并发出动作事件，源码中不再输出 `href="#builder-step-tasks"`。
