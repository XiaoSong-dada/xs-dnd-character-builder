# 玩法偏好与职业推荐完善需求

## 1. 背景与目标

车卡第 2 步（玩法偏好，`preferences`）与第 3 步（职业选择，`class`）承担"凭直觉选玩法 → 查看职业推荐 → 自由选职业"的引导职责。当前实现的推荐能力存在多处**写死**：偏好选项定义在组件里、推荐方向文案是固定字符串、职业卡片推荐分数含义不透明、推荐理由不可解释、职业成长速览只对战士写死一条。

用户需求：**推荐机制不能是写死的，应当由规则数据驱动、可解释、可扩展**，让新玩家能理解"为什么推荐这个职业"，而不是看到一串来源不明的百分比。

目标产物（本次为需求分析，不包含实现）：

- 一份现状盘点：第 2、3 步及相关规则层中所有"写死"点的位置与原因。
- 一份需求设计：偏好体系数据化、推荐引擎可解释、界面展示与真实推荐一致。
- 明确数据/类型变更范围、测试要求、完成标准与边界。

### 2.4 数据层（现状可复用的资产）

- `rules/data/classes-2014.ts:6-17`：12 个职业均含 `primaryAbilities`（主要属性）、`hitDie`（生命骰，可用于"高生存"信号）、`savingThrowAbilities`、`status`、`summary`；5 个职业含 `spellcasting`（`rules/data` 各施法者文件），可判断是否施法职业、施法属性、起始施法等级。
- `rules/data/origins-2014.ts:6-24`（种族/子种族）与 `:28-45`（背景/变体）：`recommendedClassIds` 已全部手工填充；种族还含 `fixedAbilityBonuses`（可解释"属性加值契合"）、背景含 `skillIds`（可解释"技能契合"）。
- `rules/data/feats-2014.ts:4-6`：已有 `ABILITY_KEYS` / `ABILITY_LABELS`（属性中文名）常量，被 5 个职业数据文件及页面引用，可复用于推荐理由文案（如"偏好近身作战 → 力量是主要属性"）。
- `types/rules.ts:74-87`（`ClassRule`）、`:127-145`（`RaceRule`）、`:147-162`（`BackgroundRule`）：字段齐全，推荐引擎可直接消费；`RaceRule/BackgroundRule.recommendedClassIds` 为人工维护的推荐清单，属于"推荐结论"，当前缺"推荐原因"。

### 2.5 结论

- 第 3 步的**职业列表与排序框架已数据驱动**，问题集中在：评分公式不透明、`status` 污染契合度、理由不可解释、个别展示写死（前三名徽标语义、战士速览、推荐百分比）。
- 第 2 步的**偏好选项与"推荐方向"展示整体写死**，且与第 3 步真实推荐结果无联动。
- 数据层**已有足够字段**（`primaryAbilities`、`hitDie`、`spellcasting`、`savingThrowAbilities`、`fixedAbilityBonuses`、`skillIds`、`recommendedClassIds`）支撑"可解释推荐"，不需要为推荐机制新增大块规则正文。

## 3. 需求项

> 基线约束（沿用 `docs/rules.md` 车卡顺序第 2、3 条）：**推荐只用于排序，不限制选择**；所有职业、种族、背景仍可自由选择。

### R1 偏好体系数据化（单一事实源）

1. 偏好定义从 `PreferencesStep.vue` 组件常量与 `recommend.ts` 的 `preferenceAbilities` 合并收口到规则层单一模块（建议 `rules/data/preferences-2014.ts` 或 `rules/recommend.ts` 内集中定义），结构至少包含：
   - `id`（沿用 `melee/ranged/spellcasting/support/durable/control`，保持草稿兼容）；
   - `label`（中文名，如"近身作战"）；
   - `description`（一句话说明，如"以武器近身接敌，力量或敏捷为主"）；
   - `relatedAbilityKeys`（关联属性，用于与 `ClassRule.primaryAbilities` 匹配）；
   - 可选的补充匹配信号（见 R2 第 4 条）。
2. `PreferencesStep.vue` 从规则层读取选项渲染，组件内不再出现偏好 ID/文案常量；偏好 ID 仍是 `string[]` 存于 `CharacterDraft.preferences`，**不新增草稿字段、不做 schema 迁移**。
3. 第 2 步交互可增强：点击偏好 chip 后立即给出反馈（见 R3），提示"已选 N 项，推荐将按契合度排序"。

### R2 推荐引擎可解释化（`rules/recommend.ts`）

1. **评分与状态分离**：契合度评分只由玩法信号计算；`status`（implemented/index-only）不再进入分数，改为独立的展示徽标（"资料索引"），避免资料完成度污染推荐排序。`index-only` 职业参与正常排序，但卡片上始终标注资料状态。
2. **结构化推荐结果**：`getClassRecommendation` 返回 `{ score, reasons }`，其中 `reasons` 为有序原因列表，每项包含文本与权重，例如：
   - 偏好 `melee` → "偏好近身作战：力量/敏捷是主要属性"；
   - 偏好 `spellcasting` → "偏好施放法术：该职业拥有法术施放（施法属性：魅力）"；
   - 偏好 `durable` → "偏好高生存：生命骰 d12"；
   - 无匹配 → "该职业与当前偏好无直接匹配，仍可自由选择"。
   界面展示原因明细，替代单一"匹配N项玩法偏好"。
3. **理由文本数据化**：属性名复用 `ABILITY_LABELS`（`rules/data/feats-2014.ts`）；"施法职业"从 `ClassRule.spellcasting` 推导（存在即施法职业，可带出施法属性与起始施法等级）；"高生存"从 `hitDie >= 10` 推导；`control/support` 等暂无数据信号的偏好，可给出"与该职业定位相关的玩法"级文案，但不得编造未核验效果。
4. **（可选，待确认）玩法标签**：若现有字段不足以区分部分偏好（如 `control` 与 `support` 对 12 个职业几乎无区分度），可为 `ClassRule` 增加可选字段 `playStyleTags?: readonly string[]`（如 `'frontline' | 'skirmisher' | 'blaster' | 'healer' | 'summoner'`），由数据文件维护，推荐引擎按标签匹配。该字段只服务推荐，不影响派生计算。
5. **排序与展示分离**：规则层只输出排序后的结果与原因；"前三名""推荐徽标""百分比"等展示语义由界面层决定，且百分比应改为真实可解释的表示（见 R4）。

### R3 第 2 步推荐方向实时化

1. 删除 `PreferencesStep.vue:26` 的写死文案；"当前推荐方向"改为**实时计算**：用当前偏好调用推荐引擎，取排序前 3 的职业名拼接展示（如"推荐方向：战士 · 野蛮人 · 圣武士"），偏好变更立即更新。
2. 计算位置遵守依赖方向：排序计算放规则层（`getClassRecommendation`），页面 hook 或组件经 `computed` 消费；组件内不实现推荐公式。
3. 无偏好时不显示推荐方向（或显示"选择偏好后查看推荐"），与 `canContinue` 的"至少选一项"语义一致。

### R4 第 3 步推荐展示修正（`ClassStep.vue`）

1. 删除 `index < 3` 与"推荐 N%"百分比的耦合：推荐徽标改为原因摘要（如"匹配近身作战、高生存"）或等级化标记（如"首选/次选"），不再显示来源不明的百分比；若保留百分比必须由规则层给出明确的分数语义（如"匹配度 = 命中偏好数/偏好总数"，并附原因明细）。
2. 资料状态独立展示：`index-only` 职业无论排序位置都显示"资料索引"徽标；`dm-only`/`unavailable` 按现有规则处理。
3. **职业成长速览数据化**（替换 `ClassStep.vue:33-36` 的战士写死 aside）：
   - 对**所有已选择职业**（或至少所有 `implemented` 职业）展示速览；
   - 内容从数据推导：子职选择等级（`SubclassRule.selectionLevel` / 子职数据）、施法起始等级（`SpellcastingConfig.startsAtLevel`，无则显示"不施法"）、关键检查点（`ClassRule.checkpoints` 中 `level` 与 `title`，如"1级 战斗风格"、"4级 属性提升或专长"）、生命骰（`hitDie`）；
   - 速览文案由规则层提供纯函数生成（如 `getClassGrowthSummary(classRule, repository)`），组件只负责渲染；数据变化时速览自动同步，不再手写。

### R5 种族/背景推荐理由数据化（`recommend.ts` 第 4 步联动）

1. 删除 `getRaceRecommendationReason` / `getBackgroundRecommendationReason` 中仅针对战士的特判分支，理由改为从数据推导：
   - 种族：`fixedAbilityBonuses` 与 `ClassRule.primaryAbilities` 的交集 → "体质 +2 契合你的前排生存需求"类文案；无交集时退回"属性或种族能力与该职业常见玩法契合"；
   - 背景：`skillIds` 与职业常见技能的交集 → "运动技能契合前排玩法"类文案（技能与职业的关联信号可从 `ClassRule.checkpoints` 技能检查点或数据维护的映射推导，具体信号来源待实现时确认）。
2. `recommendedClassIds` 仍作为"是否推荐"的判定依据（第 4 步 `OriginStep.vue` 的推荐排序/徽标依赖它），本次只补"为什么推荐"的解释，不改变推荐判定。
3. 若 `recommendedClassIds` 与实际属性/技能匹配结果长期不一致，需在文档（`dnd-species.md`/`dnd-backgrounds.md` 对应条目）中补充说明口径；实现阶段先保证展示一致，不强制两者完全等价。

## 4. 数据与类型变更建议

| 变更 | 内容 | 说明 |

| 新增偏好定义模块 | 偏好 ID/中文名/说明/关联属性集中定义 | 放在 `rules/data/` 或 `rules/recommend.ts`；不新增草稿字段 |

## 6. 完成标准

- 第 2 步不再包含任何偏好/推荐方向的硬编码文案，选项与推荐方向均来自规则层。
- 第 3 步推荐原因可逐项解释（玩家能说出"为什么推荐"），资料状态独立展示，职业速览对已选职业数据化展示。
- 种族/背景推荐理由无职业特判（战士分支删除），全部由数据推导。
- `test/rules/recommend.test.ts` 等新增测试通过；TypeScript 类型检查、生产构建通过；375/390/430 px 手机宽度下第 2、3 步完整流程与错误状态验收通过。
- 涉及规则行为或模块变更时，同步更新 `docs/rules.md`、`docs/frontend-architecture.md`（如新增数据模块）与 `docs/quick-build-implementation.md`；交付说明写明"已复核前端依赖拓扑，已更新/无需更新"。

## 7. 边界与不做的事

- 推荐仍只排序、不限制选择；不引入任何玩家行为数据或机器学习。
- 不改变 `CharacterDraft` 结构，不做存储迁移。
- 不扩展偏好语义到等级/属性生成方式（第 1 步的 `targetLevel`、`abilityMethod` 暂不与推荐联动；若后续需要"高等级推荐施法职业"等联动，另行评估）。
- 不为推荐编造未核验的规则效果文案；无法从数据推导的理由使用中性表述。
- `recommendedClassIds` 的人工清单保留为推荐判定依据，本次不改判定逻辑。
