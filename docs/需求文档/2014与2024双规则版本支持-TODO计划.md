## 1. 使用方式与计划边界

用户的下一步是依据本 TODO 制定更新任务。因此本文件以“可以独立展开成更新任务”的工作单元组织，明确每批目标、依赖、交付物与完成标准。

- 工作对象为 `app` 产品项目，不修改视觉原型项目。
- 保留 2014，新增 2024；以当前 1—20 级单职业能力为基线。
- 分批顺序是建议执行顺序，不是要求一次性完成全部工作。
- B00 已确认核心书范围、首批构筑、第一页、购点及数据保护政策；其余批次遵循该基线，条目核验和技术细化仍由对应批次完成。
- 每批进入实现前，先完成该批条目的规则核验，再制定具体更新任务。已有核心差异研究不能替代条目核验。
- 更新任务应保持小范围：一个职业、一组具有关联的规则、一条完整用户流程。不能直接以“全部职业兼容”作为一个任务。
- 本计划不扩展为多职业、完整战斗模拟器、房规编辑器或全部商业书目收录。

### 1.1 编号与勾选约定

- `Bxx` 为批次，`Bxx-nn` 为可追踪 TODO；后续更新任务必须引用对应编号。
- `[ ]` 表示未完成。只有交付物存在且完成标准通过，才能改为 `[x]`。
- “已创建更新任务”不等于“TODO 已完成”。准备中、执行中、受阻等状态写在任务记录中，不提前打勾。
- 如需细拆，沿用父编号增加后缀，例如 `B08-02a`，保留原编号与依赖关系。
- 条件批次若决定不做，记为“不纳入当前范围＋决定依据”，不伪装成已经实现。

## 5. 下一步更新任务的统一模板

每个更新任务至少填写以下内容，不直接复制整个批次作为一个大任务：

```markdown
# <功能范围> · 更新任务

- 对应 TODO：Bxx-nn（细拆时保留父编号）
- 当前状态：待开始
- 目标：完成后玩家能做什么
- 前置依赖：已完成条目、规则证据、尚缺决定
- 本次范围：规则版本、职业／子职、等级或条目集合
- 不包含：明确留给其他 TODO 的工作
- 规则依据：不全书章节为主；官方来源与勘误作为可选外部补充和差异记录
- 影响入口：核验后的页面、hooks、store、rules、services、types
- 实施步骤：本任务的具体代码和数据改动，先类型与规则测试再界面
- 验证：合法、边界、缺选、冲突、保存恢复及 2014 回归
- 文档同步：规则、专项资料、拓扑及需要时的公告
- 完成标准：可判定通过的条件与证据
- 结果回填：变更、检查结果、剩余问题、允许勾选的 TODO
```
